# 设计说明：为什么长这样

这份文档记录的是**踩过的坑**，不是架构赞美诗。每一条规则背后都有一次真实故障。

## 1. 第一版：并集合并（已废弃）

最初的做法简单到诱人：每台机器把自己的 `MEMORY.md` 快照放进 git，合并时取并集。

两个病治不好：

**改动要靠猜。** 判断"这两条是不是同一条"只能靠相似度，猜错就把旧版本留下来。
**删除无法表达。** 并集分不清"这条被删了"和"这台机器还没同步到它"。

结果：你改了一条记忆，下一轮它带着旧措辞回来了，两条互相矛盾地躺在上下文里。
模型读到两条冲突的事实，行为就开始飘。

## 2. 第二版：追加日志 + 折叠

每个 agent 只写自己的 `facts/<agent>.jsonl`，一行一个操作：

```json
{"op":"add","id":"f_ab12","scope":"memory","text":"...","ts":"...","by":"alpha","seq":7}
{"op":"update","id":"f_ab12","text":"新措辞"}
{"op":"forget","ids":["f_ab12"]}
{"op":"restore","id":"f_ab12"}
{"op":"pin","id":"f_ab12"}
```

`fold()` 按 `(时间, 序号, 操作类型)` 重放，得到当前事实集；`render()` 按预算挑选，
输出成 `MEMORY.md`（用 `§` 分隔，这是 Hermes 的原生格式）。

两台机器永远不会写同一个文件，所以 **git 层面不存在冲突**。谁先同步、同步几次，
结果都一样。

## 3. 三方合并：这一步错了两次

`sync` 读磁盘上的 `MEMORY.md`，和事实库对账，把差异变成操作。问题是：**怎么区分
"用户改了"和"我这台还没同步到"？**

- 第一版：凡是不在事实库里的条目就算新增，凡是事实库里没有的就算删除 →
  落后的一台会把自己的旧副本"吸"回去，把另一台刚做的修改顶掉。
- 第二版：用"连续两次缺席"判断删除 → 因为渲染会把条目写回文件，计数永远清零，
  官方删除路径**永远不生效**（这个 bug 在生产里活了几个小时才发现）。
- 现在：记录**上次渲染出的内容**（`.state/render-<scope>.json` 里的 `base`），
  只有"base 里有、live 里没了"才算删除。腾预算被丢掉的条目根本不在 base 里，
  所以永远不会被误判成删除。

这是 git 三方合并的老思路：**base / ours / theirs**，不是猜。

## 4. 为什么 pin

记忆有预算（每轮都注入上下文，一个字都是长期成本）。淘汰按时间排序，于是
"姓名 / 护照号 / 时区 / 红线规则"这些最早写进去的身份条目最先被挤掉——而且被挤出
之后，下一轮它不在文件里，会被当成"用户删了它"，两轮之后永久作废。

`pin` 让身份条目：占预算时不参与淘汰；被整文件重写时不会被自动 forget（要显式
`forget --force`）。写记忆的工具是"整份文件重写"型的，这个保护是必须的。

## 5. 为什么每次写都在锁里

`sync` 原来的顺序是"读文件 → 算 → 拿锁 → 写"。中间那段时间 Hermes 有可能写入，
它的内容会被我的渲染结果覆盖，而且不进日志——静默丢失。

现在是"拿锁 → 读 → 算 → 写 → 更新 base"，整段在 Hermes 自己的 `<file>.lock` 里。

## 6. 为什么有 chain.py

记忆放在私有 GitHub 仓库，服务器有写权限。理论上它可以**改写历史**：删掉几条，
或者伪造"这是笔记本写的"。

GitHub 的 branch protection / ruleset 对私有仓库要付费，所以这里自己做：每台机器
保存"(行数, 前 N 行的 sha256)"，每次拉取先验前缀。

- 行数变少 → 被截断
- 前缀指纹变了 → 被改写
- 只是变多 → 正常，锚点前移

锚点存在仓库**外面**（`~/.hermes/brain-anchors/`），能 push 的人改不到判断他的账本。

## 7. 为什么不用数据库 / 向量库 / CRDT

两三个写者、几百条事实、分钟级延迟。git + 追加日志已经够用，而且：

- 可读：出问题时 `cat` 就能看，不用起服务
- 可审计：每条事实有完整变更史
- 可回滚：`git revert` 就是回滚
- 零运维：没有进程要看着

等你有几十个 agent 并发写，再考虑 CRDT 或真正的共识协议。现在上这些是给自己找事。

## 8. 已知的债

- 相似度配对（0.72）是启发式：大幅改写会记成 `forget + add`，历史串不起来
- 预算淘汰按"最后修改时间"，`use` 操作没有自动触发点
- 会话正文不共享，只有摘要（`handoff`）；同步整个 `state.db` 会因为 SQLite + git
  的合并问题把库搞坏
